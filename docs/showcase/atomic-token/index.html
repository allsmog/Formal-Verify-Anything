A single-use token can succeed at most once

A security property stated as a Lean theorem, proved for every finite execution, not a handful of test schedules.

The model

One already-issued authorization token has two states, fresh and spent. A successful authorization turns fresh into spent in a single atomic step. A denied attempt changes nothing. There is no transition that issues a second token, resets a spent one, or succeeds from spent.

inductive Step : TokenState → Outcome → TokenState → Prop where
  | authorize : Step .fresh .authorized .spent
  | denyFresh : Step .fresh .denied .fresh
  | denySpent : Step .spent .denied .spent

The properties

Four theorems are proved over traces of any length and pass the kernel audit:

  • Conservation. Successful authorizations plus remaining credit equal the initial credit.
  • At most once. Any trace that starts fresh contains at most one success.
  • No reuse. Any trace that starts spent contains no successes.
  • No double success. The trace of two successful authorizations cannot occur.
theorem token_authorization_at_most_once
    (outcomes : List Outcome) (final : TokenState)
    (execution : Trace .fresh outcomes final) :
    successes outcomes ≤ 1

How the search built it

The proof tasks import only the model definitions, never the finished proofs. In the recorded run, a hand-written strategy guided the search: conservation by induction on the trace in 4 compiler calls, and at-most-once in 7, through a have that generalizes conservation before specializing it. Each final proof passed two fresh compilations and the kernel audit. This demonstrates recursive composition and kernel admission with supplied guidance; it is not autonomous discovery or a model score.

What it does not prove

The theorems are about the abstract state machine. They do not show that a real service implements it. In particular, a separate "check fresh" followed by "mark spent" is outside the model, because two callers could both pass the check. An implementation has to make consumption and success one linearizable operation. Token identity, expiry, durability, crashes and network delivery are not modeled.
