How it works

A proposal policy suggests proof steps. Lean decides whether each one works. Nothing counts until the kernel accepts the finished proof.

What the agent sees

Before any search, the runner locks the original theorem declaration, its imports and a hash of the statement. Lean then reports the current goal: the target, the hypotheses, dependent lets, universe parameters and the goal structure.

The proposer receives only that local context, the allowed imports, the remaining budget, and its own recent failed proposals with Lean's diagnostics. It never sees the parent transcript, sibling branches, or benchmark solutions. Imports of miniF2F answer modules are refused outright.

What the agent can propose

A proposal is a tactic, a case or induction split, or a structured have sublemma. A have creates a child goal to prove the lemma, then a continuation that may use it. The child cannot see its own unproved lemma; the continuation can.

How Lean checks each step

Every branch is replayed in a fresh Lean file that contains the original theorem. When a branch fails, the runner restores the exact parent plan and records the attempt: its source, diagnostics, exit code, elapsed time and an evidence digest. Probes deliberately stop after reporting their goals, so an observed state is never mistaken for a solved theorem, and earlier compiler errors invalidate a probe even if later recovery reports no goals.

Search runs under limits shared across the whole tree: compiler calls, proposal steps, recursion depth, Lean heartbeats, model tokens and wall time. Failed work is never refunded, and two compiler calls are always reserved for the final checks.

How the kernel decides

A locally closed proof is only a candidate. It is accepted after two fresh standalone compiler runs succeed, the original declaration is unchanged, and an audit of the theorem in Lean's checked kernel environment follows every transitive dependency. The audit allows only Lean's usual foundational axioms: propext, Classical.choice and Quot.sound.

The final gate rejects sorry, admit, new axioms, declaration injection, arbitrary elaborator commands and compiler-trust shortcuts. The only warning it tolerates is Lean's exact unused-variable message, which stays visible in the receipt. If the gate rejects a candidate, search resumes with the remaining budget and the compiler's feedback, and can repair an earlier sibling or change the decomposition.

Fresh processes or a persistent worker

By default every exploration call starts a fresh Lean process. With --compiler worker, a persistent Lean process keeps Mathlib loaded and starts a clean elaboration state for each candidate. In one measured workflow it finished the same proof in 17.0 seconds instead of 41.8, using more memory. Both final checks still run in fresh processes.

What it does not promise

This is bounded search. Running out of budget does not show that a theorem is false or unprovable. Lean, the pinned Mathlib artifacts, the observation bridge and any proposer command you configure are trusted; the runner is not an operating-system sandbox. Process cleanup is tested on Linux and macOS.

The search and repair reference and the runtime README cover every option in detail.
