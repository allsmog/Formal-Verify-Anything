# Codex proof proposer

`formal/src/codex-proposer.mjs` implements a real Codex CLI integration. It
requests proposals for one observed Lean goal, then lets the existing engine
and kernel decide whether they work. Its policy ID is `codex-v1`; the release
does not claim live model benchmark results where the provider cannot start.

## Run

Install and authenticate Codex using its normal supported setup. The adapter
uses the existing authentication and configuration; it does not copy credentials
or write a new home configuration.

```sh
codex login
node formal/src/cli.mjs doctor --proposer codex
node formal/src/cli.mjs solve benchmarks/tier1.json \
  --id conjunction_commutation --proposer codex --compiler worker \
  --model-token-budget 50000 --proposer-timeout-ms 60000
```

`--model MODEL_ID` selects an explicitly configured model. Otherwise the CLI's
configured default is used and metadata stores `model: null` with
`modelSelection: codex-configured-default`. That value is not a claim about the
actual resolved model. `doctor` inspects the CLI version, login status, runtime
directory writability and Lean pins; it makes no inference request.

The JavaScript interface is:

```js
import { makeCodexProposer } from './formal/src/codex-proposer.mjs';
const proposer = makeCodexProposer({
  command: 'codex',
  // model: 'an-explicit-model-id',
  timeoutMs: 60000,
  maxProposals: 6,
});
const result = await solveTheorem(problem, {
  proposer, maxModelTokens: 50000,
});
await proposer.retryCleanup();
```

## Context and command restrictions

Each call creates a new temporary working directory outside the proof repository
and writes only its strict response schema. It sends one current goal, hypotheses,
imports, remaining budgets, and node-local compiler feedback over stdin. Parent
proof files, benchmark identifiers, source solution bodies and sibling transcripts
are not included in the request. The provider may have prior training exposure
to public mathematics; this design does not establish freedom from benchmark
contamination.

The command uses `exec --json --ephemeral --sandbox read-only`, disables the
shell tool, shell snapshots, apps, plugins, remote plugins and multi-agent tools,
sets web search to disabled, and explicitly disables each configured MCP server.
An MCP inventory that cannot be parsed stops the request. The adapter does not
change managed requirements or approval settings. Tool events in a completed
response cause rejection even if the final text contains a plausible proof.
These settings do not make a hostile executable or compromised local provider
safe: the chosen CLI, its extensions and managed configuration remain trusted.

The only accepted response is a JSON object containing a bounded `proposals`
array. Each item is either `{kind: "tactic", tactic: "..."}` or
`{kind: "have", name: "...", type: "..."}`. The same lexical guards, locked
statement and independent final compilation apply to every proposal.

## Usage, failures and ownership

Token usage comes from the CLI's actual `turn.completed` event, not from text
generated by the model. Total tokens are input plus output; cached input is a
subset of input and is not added again. Reported reasoning tokens are retained
as detail, not added a second time. Missing usage remains unknown. Exactly one
completed turn is required for an accepted response.

Actual usage survives malformed proposal JSON, schema rejection, provider errors
and cleanup failures. If a failed request has no completed usage event, its
token count is `null`; the engine stops additional model search and preserves
its known subtotal. A failure before launching any model process records zero.
Version, requested model, prompt and response digests, event types, bounded
provider diagnostics and process outcome are retained. Bearer credentials are
redacted from diagnostic excerpts. Raw reasoning messages and ambient environment
variables are not saved in proof evidence.

The model-token allowance is an admission threshold across the theorem. A
request already in flight may exceed the remaining allowance; its incurred usage
is recorded and the response is refused. Time, proposal and compiler-call limits
bound the workflow, but the CLI exposes no billing cap that this adapter can
enforce. Do not interpret `--model-token-budget` as a guaranteed maximum charge.

The adapter owns each temporary directory. Cleanup failure reports its exact
path and preserves measured usage. The same proposer retains ownership through
`retryCleanup()`, which retries deletion without making another model request.
The CLI invokes this hook after each theorem and stops a batch if cleanup remains
unresolved. Subprocess timeouts terminate the owned process group on Linux.

## Verified scope of this release

Protocol tests use an explicitly labeled fixture, not a model. They exercise
scoped prompts, command isolation, malformed JSON, tool events, actual/unknown
usage, prelaunch failures, process timeout and cleanup retry. They do not prove
live-provider compatibility or model accuracy.

## Live validation

The [v2 holdout run](../../benchmarks/v2/results.md) of 25 November 2026 used
`codex-cli 0.171.0` with API-key authentication in a dedicated `CODEX_HOME`. That
home's `config.toml` set `model = "gpt-6.2-sol"` and `model_reasoning_effort =
"high"`; the CLI did not report a resolved model, so records show
`codex-configured-default`. The preflight returned a valid proposal, and all 24
holdout invocations ran: 17 were solved, four ended in provider timeouts that
reported no usage, and three exceeded the 50,000-token admission allowance.
Reported usage was 471,764 tokens. A single proposal call carried about 16,000
input tokens of fixed prompt and CLI context, so that allowance admits about three
calls per theorem.

The v2 harness performs one non-holdout preflight before any holdout call. An
unavailable provider is recorded as `BLOCKED`, with zero model theorem attempts
and no model pass rate, and the deterministic holdout still finishes.
